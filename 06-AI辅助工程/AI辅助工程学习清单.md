## 1. AI 编程工具操作

> **工具名会过期，能力类别不会。** 下面按「能力类别」组织，括号里是当前的代表产品。名字变了不影响这份清单的使用。

### 必学

**基础操作**

- [ ] IDE 内联补全与行内编辑（Cursor、VS Code + Copilot、Windsurf、Zed）
- [ ] 侧栏对话式修改，以及它和补全的分工：什么时候该用哪个
- [ ] Agent 模式的读写范围：它能碰哪些文件、会不会自己执行命令
- [ ] 上下文引用：`@文件`、`@文件夹`、`@Code`（符号级）、`@Docs`、`@Web`
- [ ] 如何让 AI 只读相关文件，而不是把整个项目塞进去

**终端 Agent**

- [ ] 终端 Agent 的初始化（Claude Code、Codex CLI、Aider、Gemini CLI）
- [ ] 让它生成补丁、运行命令、提交——以及这三件事各自的授权边界
- [ ] 权限模式：什么时候可以自动执行，什么时候必须逐个确认
- [ ] 云端沙箱与本地执行的取舍

**查看与接受改动**

- [ ] 看懂 diff：一眼分辨「实现需求的改动」和「顺手改的无关代码」
- [ ] 接受、拒绝、**部分接受**（多数工具支持按 hunk 接受）
- [ ] 改坏了怎么退：`git stash` / `git restore` / `git checkout --`
- [ ] 在接受之前先跑一遍验证（见[模块 5](#5-验证与审查)）

**规则文件**（学习优先级已变）

- [ ] `AGENTS.md` —— **优先学这个**。它已成为跨工具的事实标准：2026-09 起 Claude Code 在没有 `CLAUDE.md` 时会回退读取它，Codex、Cursor 等本就用它。一份文件多个工具通用，省掉重复维护
- [ ] `.cursor/rules/*.mdc` —— Cursor 现行的规则机制。**旧写法 `.cursorrules` 已属遗留，别再从旧教程里学**
- [ ] `CLAUDE.md` —— Claude Code 专属，现在只在需要「只对 Claude 生效」的规则时才用
- [ ] 规则文件该写什么：项目结构、依赖怎么装、跑哪个测试、代码规范、禁止事项

**Git 基础**

- [ ] 分支、diff、stash、回滚、PR
- [ ] 让 AI 写提交信息，但**提交粒度由你决定**

### 练到什么程度

能在 10 分钟内配置好环境，并让 AI 安全地修改一个文件——**改完后你能说清它到底改了哪几行、为什么改**。

## 2. 提示词与任务拆解

### 必学

**提示词结构**

- [ ] 角色、背景、目标、约束、验收标准、输出格式
- [ ] 「先出计划，再写代码」——不要在同一个回合里既要方案又要实现
- [ ] 要求引用文件行号，方便你核对，而不是通读全文
- [ ] 明确「不要改什么」——防止它顺手重构

**任务拆解**

- [ ] 把大需求拆成 5–10 个可验证的小任务
- [ ] 任务卡写法：改哪些文件、怎么验证、不要改什么
- [ ] 每个任务的完成标准要**能被机器检查**（测试通过、类型检查通过、命令输出符合预期）

**规格驱动开发（spec-driven）**

- [ ] 「先计划再写代码」的下一层：**先写规格文档**（要做什么、边界在哪、验收条件），再让 agent 照着规格实现
- [ ] 规格写进仓库（如 `specs/` 目录或 issue 正文），而不是只留在对话里
- [ ] 好处：可评审、可复用、会话上下文丢失后还能接着干
- [ ] 完整走一遍：写规格 → agent 实现 → 按规格验收

**上下文工程**

- [ ] 目标不是「喂得少」，而是「**让 AI 自己能找到需要的信息**」——工具能搜索就让它搜，别人工搬运
- [ ] 长对话会失焦：任务切换时**新开会话**，比在一个超长会话里硬撑更有效
- [ ] 分清该写进规则文件的内容（长期不变）和该放任务卡的内容（本次改动）

**防幻觉**

- [ ] 要求引用文件行号
- [ ] 要求给出验证方法
- [ ] 高风险改动时要求「先别改代码，只说方案」

### 练到什么程度

拿到一个需求，能写出**机器可验收**的任务清单，而不是让 AI 随机生成。

反例：「解析功能正常」。
正例：「`pytest tests/test_parser.py` 全绿，且 `parse()` 对空输入的返回值从 `None` 改为 `[]`」。

## 3. 软件工程基础

> AI 可以帮你写，但你必须懂，否则无法审查。

### 必学

- [ ] 需求：用户故事、验收标准
- [ ] 架构：分层、模块化、接口设计
- [ ] 代码质量：命名、小函数、单一职责、错误处理
- [ ] 测试：单元测试、集成测试、端到端测试、mock
- [ ] **测试行为而不是实现**——这条对 AI 尤其重要：AI 很容易写出把内部实现细节写死的测试，一旦重构就全红。测试应该断言「输入 → 输出」，而不是「调用了哪个私有方法」
- [ ] 调试：读栈、看日志、二分定位、最小复现
- [ ] 重构：提取函数、消除重复、保持行为不变
- [ ] 文档：README、API 文档、注释

### 练到什么程度

能判断 AI 写的代码对不对、能不能合并——而且**你的判断能说出具体理由**（哪一行有 bug、违反了哪条规范），不是「感觉不对」。

## 4. AI 辅助具体工作流

### 必学

**新功能**

- [ ] 先写测试（注意[模块 3](#3-软件工程基础)的陷阱：测试要断言行为）→ AI 实现 → 运行 → 审查 → 提交

**修 bug**

- [ ] 复现 → 日志 → 让 AI 列假设 → 逐个验证 → 修复 → 回归测试
- [ ] 关键：**先复现，再修**。没有可复现的失败用例，就无法判断 AI 是不是真修好了

**重构**

- [ ] 测试保护 → 小步改 → 对比行为

**Code Review**

- [ ] 让 AI 查 bug、安全、性能、可读性，你最终决定
- [ ] 让 AI 生成提交信息、PR 描述、发布说明
- [ ] 让 AI 解释旧代码、画架构图、写文档

**保持改动小**

- [ ] 每个改动都小到可运行、可回滚、可测试
- [ ] 一个提交只做一件事——AI 很容易在一次改动里塞进三件事

### 练到什么程度

每个改动都小到可运行、可回滚、可测试。

## 5. 验证与审查

> **这一节最该先掌握。** 让 AI 自我纠错的核心不是提示词技巧，是给它**能自动判断对错的信号**——有确定性反馈回路和没有的，是两个物种。

### 必学

**搭建确定性反馈回路**

- [ ] 类型检查：`tsc --noEmit`、`mypy`、`pyright` —— 最便宜的第一道防线
- [ ] Lint / 格式化：ESLint、Ruff、Prettier —— 规则固定，AI 无法狡辩
- [ ] 测试：单元测试 + 集成测试，且**必须真的跑起来**
- [ ] 编译 / 构建通过

**让 AI 自己使用这些信号**

- [ ] 明确要求：「改完必须运行 `npm test`，把原始输出贴出来」
- [ ] 让它自己读报错、自己迭代，而不是每轮都靠你人工转述
- [ ] 明令禁止用「跳过测试」「标记 xfail」「注释掉断言」来让检查变绿

**AI 的失败模式速查**（审查时逐条对照）

| 失败模式 | 表现 | 怎么防 |
| --- | --- | --- |
| **幻觉 API** | 调用不存在的函数 / 参数 / 配置项，文档读起来很合理 | 让它引用官方文档；运行一次就知道 |
| **改测试而非修 bug** | 测试由红转绿，但断言被改松了 | 重点审查 diff 里 `test/` 的改动，对照原始断言 |
| **伪造验证** | 报告「已修复」「测试通过」但实际没跑 | 要求贴出原始命令与输出；自己复跑一遍 |
| **静默删除** | 顺手删掉「看起来没用」的代码、错误处理、边界检查 | 审查删除行；追问「为什么这几行可以删」 |
| **过度自信** | 语气笃定但结论错误，不标注不确定性 | 让它区分「确定」与「推测」；关键结论自己验证 |
| **范围蔓延** | 一次改动顺带重构、改格式、升级依赖 | 明确「不要改什么」；按 hunk 接受 |
| **讨好用户** | 你问「这样对吗」它就附和 | 改问「这里有什么问题」而不是「这里对吗」 |

**审查清单**

- [ ] 删除的行比新增的行更需要审查
- [ ] diff 里有没有与本次任务无关的改动
- [ ] 有没有引入新依赖？是不是必需的？
- [ ] 错误处理是真的处理了，还是 `except: pass` 糊过去
- [ ] 测试的断言强度有没有被削弱

### 练到什么程度

AI 说「修好了」的时候，你能在半分钟内独立验证这句话是真是假。

## 6. 自动化与集成

### 必学

- [ ] CI/CD：GitHub Actions 的 lint、test、build、deploy
- [ ] 让 AI 读 CI 日志并修复失败
- [ ] 依赖管理：升级、漏洞扫描（Dependabot / Renovate）
- [ ] 部署：Docker、Vercel、Railway、云服务器
- [ ] **MCP（Model Context Protocol）**
  - [ ] 它解决什么问题：把文件系统、数据库、浏览器、API 以标准协议接给 agent
  - [ ] 权限边界：每个 server 能拿到什么、能做什么
  - [ ] **不要连接来源不明的 server**——MCP server 是能执行操作的代码，接它等同于交出 shell 权限
  - [ ] 自己写一个最小的 MCP server
- [ ] Agent 工作流：自动修 CI、生成文档、升级依赖

### 练到什么程度

能让 AI 帮你跑通「提交 → 测试 → 部署」的自动化流程。

## 7. 安全与合规

### 必学

**密钥与凭据**

- [ ] `.env` 写进 `.gitignore`，仓库里只留 `.env.example`
- [ ] 密钥不发给 AI（对话内容是否被记录取决于服务条款）
- [ ] 开启 secret scanning（GitHub 自带的 + gitleaks 之类）
- [ ] **一旦泄漏，要做的是轮换密钥，而不是删掉那次提交**——历史里已经有了，删不干净

**供应链与提示注入**（agent 时代的新攻击面）

- [ ] 认识到：coding agent 会**读取仓库内容**，而不只是执行你的指令
- [ ] 恶意 README、注释、issue 正文、依赖文档里可以藏指令，诱导 agent 执行操作或外传数据
- [ ] 依赖本身是攻击面：装一个包 = 让它在你机器上跑代码
- [ ] 缓解手段：agent 操作前确认；不在有敏感凭据的环境里跑不可信代码；限制网络外发

**数据隐私**

- [ ] 脱敏：客户数据、内部域名、真实用户信息
- [ ] 确实敏感时改用本地模型推理

**代码安全**

- [ ] 注入、XSS、越权、SSRF、依赖漏洞
- [ ] AI 生成的代码在这方面**没有任何额外保证**，按普通代码审

**许可证与版权**

- [ ] MIT、Apache-2.0、GPL 的区别，尤其是 GPL 的传染性
- [ ] AI 可能吐出与训练数据高度相似的代码片段：把 GPL 代码混进闭源项目有传染风险
- [ ] AI 生成代码的版权在多数辖区**目前仍无定论**——既不是「一定没问题」，也不是「一定有问题」。了解你所在辖区的现行规定与公司政策

### 练到什么程度

AI 生成的代码，你能判断有没有安全风险。

## 8. 团队协作规范

### 必学

- [ ] 规则文件分工：`AGENTS.md` 放跨工具通用规则，`.cursor/rules/*.mdc` 补 Cursor 特有规则，`CLAUDE.md` 只在需要 Claude 专属规则时用
- [ ] 哪些代码能让 AI 写，哪些必须人工（认证、支付、加密、删数据、并发）
- [ ] PR 流程、审查清单
- [ ] 提示词库、知识库
- [ ] 如何让 AI 遵守项目规范

**Agent Skills：把重复流程封装成可复用技能**

- [ ] 什么是 Skill：一段带触发条件的流程说明（`SKILL.md`），agent 匹配到场景时按需加载
- [ ] 和规则文件的区别：规则文件是「常驻的项目背景」，Skill 是「按需加载的具体做法」
- [ ] 把团队反复交代的流程写成 Skill：发版流程、写迁移脚本、特定的排查套路
- [ ] 注意工具差异：`.agents/skills` 与 `.claude/skills` 目前仍是两套目录，跨工具协作时要决定哪些技能通用、哪些专属

### 练到什么程度

别人只靠你的规则文件和技能，也能让 AI 按同样规范工作——**不需要你口头补充说明**。

## 9. 评估与持续改进

### 必学

- [ ] 记录有效提示词和失败案例（**失败案例更有价值**）
- [ ] 度量：时间节省、bug 率、测试覆盖率、**返工率**（AI 改完又被你改回去的比例）
- [ ] 成本与额度
  - [ ] 知道自己的用量上限和计费方式（订阅限额 vs 按 token 计费）
  - [ ] 便宜模型做补全和格式化，贵模型做架构和疑难 bug
  - [ ] 长会话比短会话贵得多——任务切换就新开会话
- [ ] 每周复盘：哪些 AI 用法有效，哪些无效
- [ ] 建立个人 AI 开发手册

### 练到什么程度

形成一套可复用的 AI 辅助工程系统，而不是每次从零开始。

## 最小必学清单

如果你只想先学最核心的：

1. 工具基本操作 + 上下文引用（`@文件`）
2. 写任务卡：背景、目标、约束、验收标准
3. Git 分支、diff、提交、回滚
4. **配置确定性反馈回路**（类型检查 + 测试），并要求 AI 每次改完都跑
5. 单元测试 + 让 AI 修 bug（先复现，再修）
6. Code Review：让 AI 查 bug，你决定合并
7. 规则文件：优先 `AGENTS.md`
8. 密钥不发给 AI；一旦泄漏，轮换而不是删提交
9. GitHub Actions 跑测试
