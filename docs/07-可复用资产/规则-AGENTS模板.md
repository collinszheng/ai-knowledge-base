# 规则-AGENTS 模板

> **一句话结论：** `AGENTS.md` 是给 AI 协作者的**红线和索引**，不是说明书 —— 它每次会话自动加载，所以写长了没人读、写虚了没约束。

## 来源

[体重日记](../01-AI辅助工程/项目-体重日记.md) —— 从它那份 87 行的 `AGENTS.md` 里提炼出来的。丢掉的是只有那个技术栈成立的红线（BOM、R8、Room 迁移），留下的是任何项目都成立的部分：索引表、协作纪律、验证回路，以及「单一数据源」那几条约定。

**怎么用：** 复制下面那份原件到新项目的根目录，改名为 `AGENTS.md`，把尖括号填掉。余下的骨架是跨项目通用的，按需保留、不必扩写。红线那一节（密钥不进版本库）任何项目都成立，别删。

**和别的规则文件的分工：** `AGENTS.md` 放跨工具通用规则；`.cursor/rules/*.mdc` 补 Cursor 特有规则；`CLAUDE.md` 只在需要 Claude 专属规则时才用。背景见[学习清单 · 1. AI 编程工具操作](../01-AI辅助工程/学习清单.md)。

> **这个文件名是故意的。** 很多工具会按 `**/AGENTS.md` 去 glob，重名会被误当成这个仓库自己的规则加载，所以这里叫 `规则-AGENTS模板.md` —— 前缀标类别，具体点里带 `AGENTS`，但整体不叫那个名字。

## 为什么要这么切

| 节 | 回答的问题 | 边界 |
| --- | --- | --- |
| 读之前 | 动某一块之前，先看哪份文档 | 只放索引，不放内容 |
| 红线 | 什么是**任何项目**都不许做的 | 条目极少，但绝对 |
| 工作方式 | AI 该以什么节奏跟你协作 | 跨项目通用，可直接复用 |
| 约定 | 本项目的默认做法 | 默认这样，不这样做要说原因 |
| 构建与验证 | 怎么算「做完了」 | 命令必须真实可执行，不能留占位符 |

三处容易被忽略的设计：

- **顶部那句「尖括号没填完之前不要照此执行」是安全阀。** 没有它，AI 会照着一份命令为空、索引指向不存在文档的骨架硬干。
- **红线只收「任何技术栈都成立」的条目。** 项目特有的禁令属于「约定」；写混了，红线就失去绝对性。
- **「约定」的措辞是「默认这样，不这样做要说原因」**，而不是「必须」—— 它给了偏离的合法通道，同时要求偏离被显式说出来。

## 原件

下面代码块里就是完整原件，右上角可以直接复制。

````markdown
# AGENTS.md

> **模板。** 尖括号处未填完之前不要照此执行 —— 命令是空的、索引指向不存在的文档。
> 起手新项目：填掉尖括号 → 余下的部分是跨项目通用骨架，按需保留、不必扩写。

<一句话说清这是什么项目、什么技术栈、什么形态。>

这份文件是**给 AI 协作者的红线与索引**，每次会话自动加载。保持精简 —— 只放跨项目通用或本项目反复需要的东西；细节不写在这里，写进项目自己的文档目录。

## 读之前

| 要做什么 | 先看 |
|---|---|
| **改任何设定之前** | `<决策记录>` —— 大部分「为什么不那样做」都有答案和否掉的原因 |
| 写 UI | `<设计规范>` —— 设计 token 与逐区块规格 |
| 写逻辑 | `<技术设计>` —— 架构分层、数据模型、算法 |
| 上手整件事 | `<开发手册>` —— 结构、约定、构建与出包 |

## 红线

任何项目、任何技术栈都成立。

1. **密钥不进版本库。** 写进 `.gitignore`：签名文件、口令、token 一律不提交；不能写进任何被跟踪的文件，也不能出现在提交历史里。

## 工作方式

### 进入任务

**澄清模式。** 用户提出**设计、方案、方向性想法**时（不是「改这一行」这类明确指令）进入此模式：只追问，不执行。
用户说「直接做 / 别问了 / 动手」即刻退出。

- 每轮最多问 3 个，编号列出；每个问题给 2–4 个选项 + 推荐项 + 理由。
- 一次性可查的事实自己查（读文件、查代码、搜文档），只有需要用户拍板的才提问。
- 不接受「看情况」「回头再说」：换一个具体场景重新问，或明确记为未决项。

收尾条件：**未决项清零**——只剩用户明确拍板过的决策、或已写进「未决项」清单的。清不了零就继续追问，别自己消解。

要写入时：先复述将写什么、写到哪个路径，拿到明确授权再动手。此模式下默认不写文件；仅说「记一下」不算授权。

讨论结束时先输出结构化摘要（背景与目标 / 已确定决策 / 未决项 / 风险 / 下一步），确认路径与格式后再落盘。

**给计划。** 多步任务动手前先列步骤，每步带验证方式：

```
1. [做什么] → 验证：[怎么确认]
```

能自己验证的小事不要停下来问；但有歧义、要动红线或架构的，先摆选项再动手。

### 改动中

- **先摆假设，再动手。** 有多种理解就把选项说出来，不要静默挑一个；发现更简单的做法直接讲，不要顺着往下写。
- **手术式改动**：不重构没坏的东西，风格跟现有代码走，**每一行改动都要能直接追溯到本次需求**。不顺手「改进」相邻代码、注释和格式；不加没人要的功能，不为一次性代码造抽象，不上没要求的「可配置」。
- **发现无关的死代码，说出来，别删。** 只清理**你自己这次改动**造成的孤儿（不再被引用的 import / 变量 / 函数）。

### 收尾

**逐条对着需求原文核验**（不靠「感觉做完了」），且验证回路完整跑过一遍，才算完成。提交信息写清楚**为什么改**以及**怎么验证的**。

## 约定

**默认这样，不这样做要说原因。**

- **推荐：引入决策记录（ADR）。** 每做一个「为什么不那样做」的决定就写一条，含**否掉的原因**。这是后续少走弯路的最大杠杆。
- **单一数据源。** 同一份含义只在一处定义（一个常量、一个配置、一个文档），其余地方引用它。
- **派生值不落库。** 能由已有数据算出来的（比率、聚合、格式化结果）实时计算，避免两份会漂移的真相。
- **原始数据按一种单位存储，换算只发生在显示层。**
- **不硬编码设计值。** 颜色、字号、间距全部走 token。
- **纯逻辑与平台解耦。** 算法、解析、计算部分不依赖框架运行时，可以直接跑快单测。

## 构建与验证

```bash
# ↓ 模板：换成这个项目真实的命令，未替换前不要执行
<构建命令>      # 编译
<测试命令>      # 单测，改代码后必须全绿
<产物命令>      # 出可交付产物
```

路径与工具链由脚本自动探测，**不要写死本机路径**。

**通用验证回路**：构建 → 部署 → 启动 → 观察 → 与预期/设计稿比对。
把这条链路脚本化，优先复用脚本，别手搓一长串临时命令。

- **看得见的产物要真的看**，不要凭代码推断。布局错位、残留状态这类问题只有看了才发现。
- **改完立刻验证，别攒着。** 尤其是工具链 + 非 ASCII 源文件这类组合：编码约定一旦没被验证覆盖，错误会到很后面才暴露。
````

- 「读之前」索引到[使用手册](../使用手册/README.md)和 `docs/.vitepress/sections.ts`，而不是留尖括号
- 「红线」在通用的密钥那条之外，加上了本机代理配置、构建产物、不手改 dist 三条
- 「构建与验证」写死了真实命令，并说明 `npm run docs:build` 必须提权、以及四步产物核验

## 边界

- **只管「给 AI 的约束与索引」。** 项目特有的禁令属于项目自己的「约定」；混进红线会让红线失去绝对性 —— 判断标准就是「换个技术栈还成立吗」。
- **别超过一屏。** 它每次会话自动加载，写长了没人读。细节一律外链到项目文档。
- **它不是说明书。** 架构怎么分层、为什么这么设计，写进 `docs/`；这里只留「动之前先看哪份」。
