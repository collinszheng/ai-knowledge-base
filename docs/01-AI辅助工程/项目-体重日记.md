# 项目-体重日记

> **一句话结论：** 一个纯本地的体重 / 体脂趋势记录 App —— 没有账号、没有网络权限、没有广告。它也是这套方法论第一次完整跑通的样本，[07 · 可复用资产](../07-可复用资产/) 里第一批页面大部分来自它。

> 类型：Android 应用（Kotlin + Jetpack Compose）｜规模：75 个提交、10 份项目文档、5 个验证脚本、184 个单测｜状态：已发布 1.2

## 这是什么

- 记录体重与体脂、看趋势。不做社交、不做云
- **关键约束：纯本地。** 健康数据不出设备，所以没有账号体系，`INTERNET` 权限也刻意不申请（而且有脚本断言这一点）
- 平台：Android 8.0+（minSdk 26），只保证竖屏手机，不专门适配平板 / 折叠屏

## 只对本项目成立的取舍

这些换个项目就不一定成立，所以**留在项目里，不提炼进 07**。

| 取舍 | 为什么 |
| --- | --- |
| 图表**自绘 Canvas**，不用图表库 | 设计规格极具体（恰好 4 档整数刻度、5 个 X 标签、空心圆点、渐变填充、带标签的虚线目标线），用库要一路对抗它的默认行为；而且「四色条 + 三角滑块」无论如何都得自绘 |
| **纯本地** Room + DataStore，不做云同步 | 健康数据敏感，纯本地方案隐私成本最低、开发最快。代价是换机即丢 —— 所以导出 / 备份是这块取舍的**兜底，不是可选项** |
| minSdk **26**，而不是 24 + desugaring | 开 desugaring 要多一层构建配置和依赖，而 24 覆盖的老机型占比已经很低。这个决定同时消掉了一个「不处理就崩」的坑 |
| **手写依赖容器** `AppContainer`，不引入 Hilt | AGP 9 + KSP 的版本兼容要先验证，而项目只有一个依赖图，手写够用 |
| **不拆 Gradle 模块** | 按 feature 分包；真到多模块再拆，成本可控 |
| BMI 用**中国标准**分级 | 需求原文用的词「肥胖前期」就是中国标准术语；同一体重在两套标准下会一个显示「标准」、一个显示「超重」 |
| 折线**整条连续平滑**，空缺处也画实线 | 试过「分段平滑 + 空缺虚线」，视觉上诚实但线条断续、图变难看。改成用**空心圆点**承担「这是真实测量」的语义 |
| 概览卡片**整组删除** | 最初设计是三张卡片（体重 / BMI / 体脂率）加点击切换指标。后来 BMI 预警直接进图表了，「切到 BMI 图」这个动作失去意义 —— **理由本身没错，错的是前提** |
| 不给卡片加 elevation 阴影 | `#FFFFFF` 的卡片放在 `#FFFFFF` 背景上，阴影根本看不见 |
| 不用 Paging 3 做分页 | 数据在本地，几千条一次性加载毫无压力 —— 属于过度设计 |
| 不提供 `fallbackToDestructiveMigration` | 表结构变更必须写 Migration，宁可编译期麻烦，也不要用户的记录被静默清空 |

**三处「画出来才发现」的修正**（纸面推演看不出来）：次刻度线颜色 `#F7F7F7` 在白底上几乎不可见（改成 `#F2F2F2`）；X 轴标签按数据点序号四等分，遇到有缺口的月份就漂移（改成按**位置**四等分）；X 轴画满日历刻度线让图面太碎（改成**全部不渲染**）。
