## 1. Prompt 工程

> 目标不是「写得漂亮」，而是**写出能被验收的指令**。

### 必学

**结构**

- [ ] 结构化要素：角色 / 任务 / 约束 / 输入 / 输出格式 / 验收标准
- [ ] 把形容词换成可判定的条件（「专业」→「给出 3 个来源并标注年份」）
- [ ] 明确**不要做什么**（防跑偏、防顺手扩写）
- [ ] 用分隔符把「指令」和「用户数据」隔开，减少指令被数据污染
- [ ] 输出格式：优先用 JSON schema / structured output，而不是「请输出 JSON」
- [ ] 确定性任务用低温度甚至 `temperature=0`；创造类任务才调高

**示例与推理**

- [ ] Few-shot：示例数量、**顺序敏感**、格式必须与期望输出一致
- [ ] Few-shot 的选择比数量更重要（挑边界案例，别挑典型样例）
- [ ] 思维链（CoT）：**什么任务该用、什么任务纯属浪费 token**
- [ ] 自洽性（self-consistency）：多次采样投票，代价与收益
- [ ] ReAct：推理与行动交替的基本模式
- [ ] 长上下文里的「迷失中间」：关键信息放头尾，别塞在中间

**安全**

- [ ] Prompt 注入的两种形态：**直接注入**（用户输入）与**间接注入**（检索到的文档、网页、issue 正文里藏的指令）
- [ ] 防御思路：数据与指令分区、最小权限、输出校验、对外发动作要确认
- [ ] 不把密钥、内部 URL、系统提示词暴露给模型输出

**工程**

- [ ] Prompt 有版本、能回滚（像管理代码一样管理它）
- [ ] 每次改 prompt 都跑一遍评测集，而不是只看几个样例

### 练到什么程度

拿到一个模糊需求（「帮我写个客服机器人」），**能改写成包含验收标准的指令**，并说出它会在哪些输入上失败。

## 2. RAG

> 先问一句：**你真的需要 RAG 吗？** 很多问题靠更好的 prompt 或更长的上下文就解决了。

### 必学

**链路与切分**

- [ ] 完整链路：切分 → 向量化 → 检索 → 重排 → 组装上下文 → 生成
- [ ] 什么时候不需要 RAG（数据量小、上下文放得下、问题不需要精确出处）
- [ ] 切分策略：固定长度 / 递归 / 语义 / 按结构（标题、段落、代码块）
- [ ] Chunk size 与 overlap 的权衡：太大检索不精准、太小丢上下文
- [ ] 保留元数据：来源、章节、时间 —— 后面过滤和引用都靠它

**检索**

- [ ] Embedding 模型选型：维度、语言支持（中英差异）、领域适配
- [ ] MTEB 之类榜单的局限：榜上分数与你的任务相关性有限
- [ ] 相似度度量：cosine / dot / L2，以及**归一化之后它们的等价关系**
- [ ] 向量库定位：FAISS / Milvus / Qdrant / pgvector —— 并知道**几千条数据用 NumPy 就够了**
- [ ] ANN 索引：HNSW / IVF / PQ 各自牺牲了什么换速度
- [ ] 混合检索：BM25 + 向量 + RRF 融合 —— **纯向量会漏掉型号、人名、错误码这类精确关键词**
- [ ] Rerank：召回后加 cross-encoder 重排，收益通常比调 chunk 大
- [ ] 查询改写：指代消解、多查询展开、HyDE
- [ ] 元数据过滤与权限隔离（多租户下**必须**带过滤，否则串数据）

**生成与排查**

- [ ] 上下文组装：去重、排序、长度预算、标注来源
- [ ] 要求模型**只依据给定材料**回答，并允许它说「材料里没有」
- [ ] 增量更新与失效：文档变了怎么处理旧向量
- [ ] **RAG 效果差的排查清单**：先分诊是「没召回」「召回错了」还是「召回了但没用上」
- [ ] 检索层与生成层**分开评测**（见[模块 5](#5-评测)）

### 练到什么程度

面对一个「答错了」的 case，**能定位是检索问题还是生成问题**，并给出验证方法（例如先把召回片段打印出来看）。

反例：「换个更大的 embedding 模型试试」。
正例：「检索 top-5 里根本没有正确片段，属于召回失败 → 先查切分是否把答案切断了，再考虑换模型」。

## 3. Agent 与工具调用

> 最重要的一条判断：**大多数场景固定 workflow 比 agent 更稳、更便宜。**

### 必学

**基础**

- [ ] Agent 的基本循环：观察 → 思考 → 行动，以及它和单次问答的本质区别
- [ ] Function Calling / Tool Use 协议：schema 定义、参数校验、返回格式
- [ ] **工具的描述就是 prompt** —— 命名与描述直接决定调用准确率
- [ ] 工具粒度：太细 → 轮次爆炸；太粗 → 不可控
- [ ] 什么时候该用固定 workflow（能穷举分支就别交给模型决策）

**记忆与规划**

- [ ] 记忆分层：短期上下文 / 长期存储 / 摘要压缩
- [ ] 摘要压缩的时机与信息损失
- [ ] 规划模式：任务分解、Plan-and-Execute、ReAct、树搜索
- [ ] 长任务的状态管理：中间结果存哪、怎么保证可恢复

**稳定性与安全**

- [ ] 错误恢复：工具报错、参数非法、模型原地打转
- [ ] **必须设硬边界**：最大轮数、超时、token 预算
- [ ] 幂等性：重复执行同一个工具调用会不会造成破坏
- [ ] 不可逆操作（删数据、发消息、付款）**必须人工确认**
- [ ] 工具即权限 —— 给 agent 的能力范围就是它的攻击面

**工程**

- [ ] 可观测性：每一步的输入输出都要留 trace，否则无法调试
- [ ] 框架对比：LangGraph / AutoGen / CrewAI —— 以及**先手写一个循环**再决定要不要框架
- [ ] 多智能体：什么情况下真的需要（多数时候不需要）
- [ ] 成本：agent 的 token 消耗常是单次问答的 10–100 倍

### 练到什么程度

**不用任何框架，手写一个能用 2–3 个工具的 agent**，并说清「这个问题为什么需要 agent 而不是固定流程」。

## 4. 微调

> 先做决策，再动手。**微调是最后手段，不是第一手段。**

### 必学

**决策**

- [ ] 三选一的判断依据：改 prompt / 上 RAG / 做微调
- [ ] 判断表：知识更新用 RAG、格式与风格用微调、逻辑与规则用 prompt
- [ ] 微调解决不了「模型不知道的事」——那需要检索或继续预训练

**方法**

- [ ] 全参数微调 vs PEFT，各自的门槛与代价
- [ ] LoRA：低秩假设、`rank` / `alpha` / `target_modules` 怎么选
- [ ] QLoRA：4-bit 量化 + LoRA，单卡能做什么、牺牲了什么
- [ ] LoRA 的学习率通常要比全参微调**高一个量级**
- [ ] 训练轮次：为什么 LoRA 常常 1–3 个 epoch 就够、多了会过拟合

**数据与验收**

- [ ] 数据构造：格式一致性、去重、难度分布、必要的负例
- [ ] 数据质量 >> 数据数量（少量高质量常胜过大量噪声）
- [ ] 常见失败模式：过拟合到格式、灾难性遗忘、loss 正常但输出变差
- [ ] **评估必须与 base 模型对比**，且用留出集，不能只看训练 loss
- [ ] 合并与导出：merge LoRA、量化导出 GGUF
- [ ] 成本与时间估算（一次 LoRA 要多久、花多少钱）

### 练到什么程度

能画出一张决策表回答「这个问题该用提示词、RAG 还是微调」，并且**用 LoRA 完成一次带评估的微调**（哪怕数据只有几百条）。

## 5. 评测

> **这一节是全篇最重要的。** 没有评测，你就没有反馈回路，所有改动都是凭感觉。

### 必学

**建评测集**

- [ ] 三个来源：真实用户日志、人工构造、模型生成 + 人工审核
- [ ] 规模不必大：**50–200 条覆盖边界的样本，远胜 5000 条随机样本**
- [ ] 每条样本要有明确的「正确」判定方式（答案、要点、或评分标准）
- [ ] 划分：开发集用来调，留出集只在最后看一次
- [ ] 评测集要能一键运行（一条命令给出分数），否则你会懒得跑

**评测方法**

- [ ] 自动指标 vs LLM-as-Judge 的适用边界
- [ ] LLM-as-Judge 的已知偏差：**位置偏差、长度偏差、自我偏好**
- [ ] 缓解手段：成对比较、交换顺序取平均、给出明确评分标准、用不同模型交叉评判
- [ ] 生成任务的 BLEU / ROUGE 为什么对开放生成几乎没用
- [ ] 结构化任务优先用**可编程的判定**（字段是否齐全、数值是否相等）
- [ ] RAG 分开测：检索层（recall@k、MRR）与生成层（faithfulness、answer relevance）
- [ ] 幻觉与事实性评测必须有**外部依据**，不能只问模型自己

**回归与线上**

- [ ] 把评测集接进 CI：改动前后自动跑、分数下降就报警
- [ ] 线上评测：A/B、人工抽检、用户反馈信号（点赞/采纳率）
- [ ] 警惕对着测试集调参导致的虚假提升

### 练到什么程度

为一个具体任务建出 **50 条以上的评测集**，并能一条命令跑出分数、与上一版对比。

> **这是整份清单里最该先做的一件事**，比你换个更好的模型更有价值。

## 6. 工程化与成本

> 上线的门槛不是「能跑」，而是**可观测、可回滚、算得清成本**。

### 必学

**性能**

- [ ] 延迟拆解：排队 / prefill / decode / 网络，以及 **TTFT** 与 **TPOT** 两个指标
- [ ] 流式输出：为什么它不降低总时长，却大幅改善体感
- [ ] Prompt caching 的适用条件与命中率
- [ ] 语义缓存的收益与坑（相似问题给出错误答案）
- [ ] 批处理与并发：吞吐和延迟的取舍
- [ ] 重试、超时、降级（小模型兜底、返回旧答案）

**成本**

- [ ] 成本核算：输入与输出**单价不同**，长上下文主要吃输入
- [ ] 省钱手段排序：缩短上下文 → 缓存 → 模型分级路由 → 批处理
- [ ] 知道自己的额度与计费方式（订阅限额 vs 按 token 计费）
- [ ] 给一次请求画出「时间 + 成本」分解，找出最值得优化的那一项

**可靠性**

- [ ] 结构化输出的 schema 校验 + 失败重试
- [ ] 可观测性：日志、trace、token 计数、失败率、延迟分位数
- [ ] 版本管理：prompt / 模型 / 评测集**都要能回滚**
- [ ] 安全：注入、越权、数据外传、PII 脱敏

### 练到什么程度

能对自己做的东西说清：**P95 延迟是多少、每次调用多少钱、出问题怎么回滚。**

## 最小必学清单

如果你只想先学最核心的：

1. 结构化 prompt：任务、约束、输出格式、**不要做什么**
2. 认识间接 prompt 注入（来自检索内容），并做基本防护
3. RAG 链路：切分 → 向量化 → 检索 → 组装
4. **混合检索**：纯向量会漏精确关键词
5. RAG 排查分诊：没召回 / 召回错 / 没用上
6. 建 50 条评测集，且一条命令能跑
7. LLM-as-Judge 的三个偏差与缓解手段
8. 判断该用 prompt、RAG 还是微调
9. LoRA 微调一次，**与 base 模型对比评估**
10. 算清一次请求的延迟与成本分解
